第八部分：三项根因和源码修复

根因一是通讯版升级后的 Shizuku 客户端脚本仍然硬编码旧通讯版本之前使用的端口 18926，而 v349 以后的通讯版真实桥端口已经是 18936。桥服务与授权本身正常，只有客户端脚本指错端口。端口 18936 的 status 当时一直返回 installed、running、granted、enabled 全部为 true。

事故现场临时修复过五个通讯版运行时脚本，把 18926 改为 18936：
/data/user/0/com.codex.mobile.pocketlobster.test/files/usr/bin/shizuku-shell
/data/user/0/com.codex.mobile.pocketlobster.test/files/usr/bin/shizuku-shell-status

/data/user/0/com.codex.mobile.pocketlobster.test/files/usr/bin/codex-capabilities

永久源码修复位于 CodexForegroundService.ensureHostServer。每次宿主健康启动都先调用 serverManager.ensureShizukuBridgeScripts，再检查和启动服务，从而让覆盖升级后也重新生成当前包名对应的端口脚本。文件位置：
android/app/src/main/java/com/codex/mobile/CodexForegroundService.kt

根因二是 src/server/codexProviderAdapter.ts 原先只把 OpenAI Responses 请求和第三方响应原样透传。OpenAI 原生自定义工具 custom 在只支持 function 的第三方兼容接口上被错误处理，第三方返回 function_call，Codex 宿主期望 custom_tool_call，因此工具变成 unsupported call。第三方还返回任意 UUID 或哈希前缀的 message、reasoning 和 function_call 编号，切回 OpenAI 后被严格校验拒绝。

永久修复新增 src/server/codexProviderProtocol.mjs 和对应类型声明。向第三方发送前，把 custom 工具定义转换成 function 工具，把 custom_tool_call 历史转换成 function_call，把输入封装为 input 字符串字段。第三方响应返回后，把属于自定义工具的 function_call 和流式 arguments 事件转换回 custom_tool_call 与 custom_tool_call_input 事件，并缓存流式参数直到完整输入可解析。所有 message、reasoning、compaction、function_call、custom_tool_call 项目的外来编号都会被转换为稳定且符合 OpenAI 前缀要求的编号，所有 item_id 引用同步改写。

线程路由迁移修复位于 src/server/codexAppServerBridge.ts。切换提供商时仍清理不可跨提供商复用的 reasoning 与 compaction；切回 OpenAI 时即使路由记录已经显示为 OpenAI，也会扫描并修复持久化线程里的非法响应项目编号和引用。迁移失败会恢复原文件，诊断会记录 repairedResponseItemIds 数量。

根因三是 src/api/codexGateway.ts 的 thread/list 历史分页请求省略 modelProviders。Codex app-server 的正式协议定义明确规定：modelProviders 存在但为空数组表示包含所有提供商；参数省略时可以按当前提供商筛选。永久修复是在每一页 thread/list 请求里显式传 modelProviders: []，历史列表因此与当前选择的模型提供商解耦。

第九部分：为什么此前测试版验证没有发现事故
